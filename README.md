This repository contains both exercises from the assignment:

1. **`/xlsform`** — an ODK XLSForm that digitizes the paper form for mobile/tablet data collection.
2. **`/pug-pdf`** — a Pug HTML + Node.js pipeline that regenerates the paper form as a print-accurate, data-driven PDF.

Both exercises describe *the same form*, from the two different angles the internship asks for: XLSForm is for **capturing** the data, Pug HTML is for **presenting/printing** it back out. Where it mattered, I kept the field names, choice lists and business rules consistent between the two, and call that out below.

## 1. XLSForm (`/xlsform/criminal_risk_assessment.xlsx`)

Open it in Excel/Sheets, or drop it straight into [https://getodk.org/xlsform/](https://getodk.org/xlsform/) to preview it as ODK Collect would render it.

### What it covers

- All 10 numbered identity fields from page 1, the consent block (with a signature capture and conditional witness field), the "two pieces of ID" checklist, and every field on page 2 (agency, reason for assessment, assigned worker, designate contact info, request date).
- **Required fields** follow the form's own asterisk convention (page 2 explicitly says "SECTIONS MARKED WITH AN ASTERISK (\*) ARE REQUIRED"; page 1 does not asterisk anything, so only the fields any reasonable intake process would insist on — name, DOB, sex — are marked required there).
- **Conditional logic (`relevant` columns):**
  - Signature and witness fields on page 1 only appear if consent status = *Consented*.
  - "Other, specify ID" and "MB Driver's Licence number" fields only appear if the matching checkbox is ticked.
  - A warning note on page 2 appears **only if** the selected "Reason for Risk Assessment" requires consent (*Place of Safety* / *Kinship or Customary Care Agreement*) **and** the person was recorded as *Unconsented* on page 1 — this is a real cross-field business rule pulled directly from the form's own text ("Must have consent: Place of Safety / Kinship or Customary Care Agreement").
- **A `constraint`** on the ID checklist enforces "at least two pieces of identification," exactly as the form's red-highlighted note requires, with a custom validation message.
- **A `calculate`** field concatenates First + Last Name from page 1 and re-displays it, read-only, on page 2, matching the form's own instruction that "Name of Person Being Assessed... must match information on page 1" — instead of trusting the user to retype it correctly, the form fills it in for them.
- `request_date` defaults to `today()`.
- Field/choice naming is XLSForm-idiomatic snake_case, following the same sheet structure (`survey` / `choices` / `settings`) as the sample form you provided.

### How it was built and checked

`build_xlsform.py` generates the `.xlsx` from a plain Python data structure (openpyxl) rather than being hand-edited in Excel — this makes the whole field list reviewable as code and reproducible:

```bash
cd xlsform
python3 build_xlsform.py
```

It was then compiled with **pyxform** (the same engine `getodk.org/xlsform` runs) to make sure it's a valid XForm, not just a spreadsheet that looks right:

```bash
python3 -m pip install pyxform
python3 -m pyxform.xls2xform criminal_risk_assessment.xlsx validation/compiled-xform.xml
```

Output is saved at `xlsform/validation/pyxform-validation-log.txt` (`Conversion complete!`, zero errors — one harmless advisory warning about the signature image field, which is already addressed via the `max-pixels` appearance).

### Assumption called out

Field 5 on the source PDF literally reads **"MALE ☐ MALE ☐"** — almost certainly a typesetting/OCR artifact where the second box should read "FEMALE". I've modelled it as the evident intent (Male / Female) and flagged this explicitly with a field hint in the form itself, so it's visible to anyone reviewing the form and is called out in the demo video rather than silently guessed at.

## 2. Pug HTML → PDF (`/pug-pdf`)

```bash
cd pug-pdf
npm install
npm run render -- src/data/sample-request-1.json
# -> writes pug-pdf/output/sample-request-1.pdf
```

Three ready-made sample data files are included (`src/data/sample-request-1.json`, `-2.json`, `-3.json`) and their rendered output is committed at `pug-pdf/output/*.pdf` so you can see the result without running anything.

### What it demonstrates

- **Image / letterhead** — the Manitoba Families logo (extracted from the source PDF itself) appears at the top of every physical page.
- **Header & footer, with real page numbers** — these are *not* drawn inside the page content. They're generated by Chromium's own PDF header/footer engine (`page.pdf({ headerTemplate, footerTemplate })`), the same mechanism the source PDF's own "Revision date / Page X of Y" footer uses. That means if the content ever grew to 3 or 4 pages, the header and footer would still repeat correctly and the page count would still be accurate — it isn't hardcoded.
- **Dynamic data** — one Pug template + one JSON file in → one filled PDF out. Text fields, the Male/Female checkbox, every "two-piece ID" checkbox, and the three-way "Reason for Risk Assessment" radio all render based on whatever the JSON says.
- **Cross-page dynamic behaviour** — sample 2's JSON has `consent.status = "unconsented"` and `request.reason = "kinship_customary_care"` (a reason that requires consent). The template mirrors the same business rule as the XLSForm and prints a red warning banner on page 2 — sample 1 and 3 don't trigger it. Compare:
  - `docs/screenshots/sample2-page1-unconsented.png` (page 1 — Unconsented is checked, no signature)
  - `docs/screenshots/sample2-page2-warning-banner.png` (page 2 — warning banner appears)
  - `docs/screenshots/sample1-page1-consented.png` (a consented case, for contrast)

### How it's put together

- `src/scripts/view-model.js` — turns the raw JSON into a flat, pre-formatted "view model" (dates formatted, checkbox booleans computed, warning flag computed). All the business logic lives here in plain JS, not scattered through the template.
- `src/views/criminal-risk-assessment.pug` — the actual two-page layout, built from a couple of small reusable mixins (`+field`, `+checkbox`) so every row on the page is drawn the same way.
- `src/views/partials/header-template.pug` / `footer-template.pug` — compiled separately and handed to the PDF engine's native header/footer slots.
- `src/styles/form.css` — print styling, inlined into the page at render time (kept as a normal, separate `.css` file for readability, not string-concatenated into the Pug).
- `src/scripts/render.js` — the glue: Pug → HTML → Chromium → PDF. Uses **Playwright's Chromium** (already available in this environment) purely as the print engine; Puppeteer would work identically since the two libraries share the same underlying Chrome DevTools Protocol PDF API — this was a tooling choice, not a requirement from the assignment.
